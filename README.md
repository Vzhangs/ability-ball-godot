Ability Ball Lab 是一个用 Godot 4 编写的原创程序化“能力球”战斗与短视频生产项目。一个或多个阵营可以各自携带有序阵容，并让一个或多个带有独立规则的主球在封闭竞技场中依靠初速度、墙面反弹、球体碰撞和显式技能自动战斗；画面、粒子和大部分音效由代码实时生成，个别角色化语音使用在对应球模块内声明、来源可追溯的真人或角色原声短采样。

界面默认选中“吸血鬼 VS WDC”，但该组合没有任何专用场景、能力档案或数值覆盖。所有球可以任意配对，始终使用同一套通用规则和各自唯一的持久化配置，默认时限为 120 秒。

## 运行

需要 Godot 4.7 或更新版本。导入仓库中的 `project.godot` 后运行主场景；Linux 也可执行 `godot --path .`。

球库含 30 个小球，支持单挑、擂台接力、多方混战、团队混战和 BOSS 战。

macOS 双击 `启动能力球.command` 或运行 `./tools/play_local.sh`，窗口默认在后台启动；点击窗口后选择阵容并开始对战。

```bash
./tools/play_local.sh
```

后台启动保留真实窗口和原生渲染，不自动切换当前应用；后台实例不占用 Dock / ⌘Tab 应用入口，可直接点击窗口操作；需要前台启动时使用 `./tools/play_local.sh --foreground`。首次带窗口启动会使用 Xcode Command Line Tools 编译本项目的 macOS 启动辅助库，缓存写入 `artifacts/local-launch/`。可用 `GODOT_BIN` 指定引擎路径。直接运行 Godot 或从编辑器启动不经过此入口，仍可能自动聚焦。

操作：

- 交互式启动只进入待开局状态，不创建默认战斗；选好玩法、阵容和种子后点击“开始对战”才创建 `BattleSimulation`
- `空格`：暂停/继续
- `R`：使用相同种子重开
- `N`：使用随机种子重开
- `1`、`2`、`4`：切换演算速度
- 在左侧“对战控制台”输入任意非零整数种子
- 使用左侧玩法下拉框切换单挑、擂台接力、多方混战、双方大混战；当前玩法的完整阵容始终直接显示在左侧独立配置栏，不再经过第二个阵容弹窗
- 点击阵容中的球名打开同一个卡片式球库；卡片直接展示球模型和球名，悬浮显示完整能力说明，也可按球名、ID 或能力关键词搜索。除单挑外，每支队伍标题行都可直接编辑阵营名，留空则恢复红队、蓝队、黄队等默认名称；改名只改变观众可见文字，不改变队色、头顶三角或敌我关系。多人玩法可在标题栏直接加球；同队球按从上到下的顺序纵向排列，可删除或上下调整出场顺序。多方混战还可直接新增或删除阵营。阵容编辑完成后点击“开始对战”生效
- 点击左侧录制菜单选择 24、30、60 或 120 FPS，并在后台按当前球、种子和持久化配置完整重演生成 MP4；当前窗口可以继续观看，成片不包含左侧配置栏，底部留白会循环滚动介绍当前上场球的能力
- 点击“玩法设置”修改当前玩法自己的默认对局时限、实际竞技场宽高、录制帧率、胜负揭晓延迟、擂台落败提示时间与字号、伤害数字字号和停留时间；五种玩法互不覆盖
- 点击“球参数”后使用与阵容一致的卡片式球库选择任意球，修改该球简介、本体、技能和附属实体参数，再点击“保存并应用”

通用球参数按球 ID 独立保存在 `user://ability_ball_settings.json`；BOSS 战使用独立的 `user://ability_ball_boss_settings.json`，首次未保存时使用各球 Schema 默认值。修改 BOSS 战中的血量、伤害、附属物参数或简介不会覆盖通用配置，反向修改通用配置也不会影响 BOSS 战。切换玩法和重新启动会读取对应文件。球简介也是每个球自己的持久化配置，保存后选球卡片详情、悬浮提示和阵容说明都会读取同一份当前简介。例如把分身球生命值改为 145、分身上限改为 7 并重写简介后，它在当前参数档案中的后续对局都继续使用这组值；其他球保留各自的配置。重开、随机种子、切换对手和重新启动项目都不会恢复默认值。“恢复此球默认”只重置弹窗当前选中的球，并在“保存并应用”后持久化。

交互窗口使用 1180×1280 逻辑画布：左侧 420 px 是独立对战配置栏，右侧保留标题、固定 650 px 视觉宽度的战斗视图和胜负信息；普通模式使用正方形竞技场时战斗视图高 700 px，擂台会为专属观众 HUD 增加顶部空间。战斗视图围绕右侧区域的稳定垂直中心排列，竞技场增高或变矮时从中心向上下两侧伸展，外框高度按纵横比变化而不缩放视觉宽度。擂台观众 HUD 另保留 24 px 底部可视余量，440×740 的竖向竞技场连同出阵队列、时间和当前球血条仍完整进入交互画布与成片。每支队伍是一个纵向分组，加球会在该队下方向下增加一行；阵容区完全禁用横向滚动，球或队伍较多时统一使用纵向滚动。开始、录制、种子和设置按钮始终固定在侧栏下方。录制呈现使用 720×1280 逻辑母版和 1080×1920 原生渲染目标，不创建或录入左侧配置栏；简介区始终紧随战斗视图底部并填满剩余高度，短竞技场会让简介自动上抬和加长，长竞技场则为简介保留最小可滚动高度，二者永不相交。


命令行也可以覆盖单局时限：

```bash
./tools/play_local.sh -- --time-limit=90
```

## 战斗画面

竞技场采用深蓝色分层地面、细网格、缓慢转动的环形刻度与漂浮微光，边界保留清晰的碰撞轮廓，并带有柔光护边和四角灯条。

主球具有接地阴影、随球种配色变化的柔光与连续渐隐拖尾；通用弹丸带有方向尾焰和亮核，光束采用外晕、彩色主体与高亮内芯。撞墙在实际接触点产生碎光和扩散波，球体碰撞使用短促闪光、冲击环与拉长的火花，死亡时增加向外飞散的余烬。伤害数字带暗色描边。

HUD 使用简洁的镜像血条与独立计时数字。血条表面叠加半透明渐变、柔和反光和屏幕模糊采样形成的毛玻璃质感。血量数字立即更新，填充在短促过渡后收敛，扣血时同色残影逐渐退去，并从退去的边缘散落细小碎光；回血带轻微绿色反馈。所有 HUD 碎光合计最多 48 个，暂停冻结动画，重开清空反馈。多人面板保留阵营存活数量，接力队列继续展示当前、候补和落败小球；超额生命保留真实数值，最后十秒的计时文字变为暖色。

球体按身份采用五类材质：吸血鬼、火焰与植物等使用连续渐变；音速、列车长、科比等保留大面积纯色珐琅；黑洞、尤里、浮游炮与哥德巴赫球带旋转分段光环和流动亮点；机械与装甲球使用斜向金属反光；寒冰、分身和女刀球采用折光晶面与呼吸星芒。原有武器、牙齿、徽记、像素脸和成长形态继续叠绘在球面上。选球卡片与实战共享球体材质，纹理使用独立平滑过滤与 mipmaps，并最多缓存 64 张，不改变像素图案的显示方式。

通用粒子使用复用缓冲区的三层 GPU 实例绘制，最多同时保留 640 个粒子和 96 个冲击环，密集碰撞时优先显示新反馈。暂停冻结特效，继续后接着播放，重开清除上一局效果；视觉随机与战斗随机彼此独立。

## 结算战报

对局结束并经过胜负揭晓延迟后，战斗区域显示可滚动的完整战报，保留胜负、结束原因、耗时和种子。每个阵营按出阵顺序逐球列出合计，再拆分“本体与技能”及各类独立附属单位。同名球通过阵营和出阵序号区分；擂台中已落败的球保留历史，未出场候补明确标为“未上场”。

- **造成伤害**：实际扣除的主球与附属单位生命；无敌拦截、过量伤害和自身损血不虚增输出。
- **承受伤害**：实际损失的生命，包含自损与没有攻击来源的损耗；这些损耗另有提示，不伪造攻击者。
- **回复量**：该球或单位实际恢复的生命，不统计未生效的过量治疗；允许突破上限的回血按实际增加量记录。治疗来源另显示“治疗贡献”，例如向日葵提供治疗、拾取阳光的球获得回复。
- 附属单位按自身类型汇总，例如火豌豆射手、冰豌豆射手、豌豆机关枪、向日葵、分身、浮游炮、坦克、士、无柄刀、黑白棋子及火车头与车厢。其发射的子弹和施加的持续伤害归入相应单位类型，不重复叠加到本体行；主球合计只将明细加总一次。
- 永久转移所有权只影响后续记录。控制前的贡献留在原主球，控制后的贡献列在当前控制者下，并标记“受控”及原阵营、原主球和出阵序号。已经发射的弹丸、已经施加的持续伤害保留产生时的来源，即使原单位随后被控制、被吞噬或死亡，也不会改写历史归属。

交互窗口和录制呈现都会在开头停留后自动从头滚动至最底部，表头和统计口径保持固定。最后一行展示完并停留后结束自动滚动，交互窗口仍可手动翻阅；录制必须等实际滚动完成后才结束片尾，不依赖预估时长提前退出。开始新局会创建全新账本；每局最终战报同时写入日志的 `combat_report` 字段及模拟快照，不依赖结算时仍在场的实体反推数据。

## 架构总览

项目采用“模块化单体 + 能力契约”。只有一个 `BattleSimulation` 和一个 `BattleView`；所有球及其附属实体都以自动发现的插件模块接入，不存在按组合匹配的特殊场景层。

```text
Main
 ├─ GlobalSettingsStore ─> user://ability_ball_global_settings.json
 ├─ BallSettingsStore ──> user://ability_ball_settings.json
 ├─ BattleLogger ────────> builds/logs/<日期>/<battle-id>.jsonl
 ├─ BallRegistry ───────> balls/<id>/module.gd + 该球参数覆盖
 └─ BattleView ─────────> BattleSimulation <── BattleSetup
                            │
                            ├─ BallAbility
                            ├─ BallEntity
                            ├─ BallStatusEffect

依赖方向：具体球 → 稳定契约 → 通用核心
禁止方向：通用核心 → 具体球；球 A → 球 B
```

### 运行时调用链

1. `Main` 启动时读取当前玩法的独立全局设置档和所有球参数。玩法设置决定该玩法新对局的时限、竞技场尺寸、录制帧率、胜负揭晓延迟与伤害数字表现；球参数按球 ID 交给 `BallRegistry`。切换玩法会分别保留当前会话中该玩法的阵容与自定义阵营名，并恢复目标玩法自己的阵容、名称、全局设置和对应球参数档案；创建或重开对局不会清空当前会话配置。
2. `BallRegistry` 扫描 `scripts/balls/*/module.gd`，校验每个球自己的参数 Schema，应用该球的覆盖值后按 `sort_order` 生成唯一球库；UI、CLI、测试和视频工具都读取这份球库。
3. `Main` 将单挑、擂台接力、多方混战、BOSS 战、双方大混战归一化为同一种 `BattleSetup`。`BattleSimulation` 根据阵营阵容和同时上场数创建独立 `FighterState`、`fighter_uid` 与 `BallAbility`；所有主球分别在 360° 内按种子生成可复现的初始方向，并以 60 Hz 固定步长推进同一套物理与技能。
4. `BallAbility` 只通过 `BallBattleContext` 造成伤害、治疗、生成实体、施加状态、申请通用世界停顿、读取确定性随机数和发送通用战斗事件。
5. `BallEntity` 与 `BallStatusEffect` 各自管理附属物和跨帧状态；核心只调用稳定生命周期，不识别具体球种。
6. `BattleView` 读取模拟快照，并将球体、附属物、可选实体 HUD 和状态覆盖层的绘制委托给 `BallVisual`、`BallEntity` 和 `BallStatusEffect`；表现层不能反向修改玩法状态。

## 架构原则

### 1. 一个运行时事实源

所有模式与组合都由 `BattleSimulation` 演算、由 `BattleView` 展示。模式生成统一的 `BattleSetup`；BOSS 战仅由入口选择独立持久化球参数，不另设能力脚本、额外强化、特殊出生或物理规则。球模块和模拟器不读取参数文件。

- `duel`：两个阵营，各一个主球；
- `relay`：两个阵营默认命名为红队和蓝队，也可为当前配置改成任意合法显示名，各一个活跃主球；主球死亡后先单独完成退场演出，在当前玩法可配置的落败提示期间冻结战斗，只显示对应队色的球名落败悬浮文字，再在原位置按有序阵容换入候补；对手和其他友方的位置、生命、速度、技能计时、状态、视觉实例与附属物保持原对象和原数值；观众 HUD 只显示双方当前上场球的独立血量，顶部缩小球模型由红方从左向中央、蓝方从右向中央紧凑排列，当前球高亮、下一位预告、已败球覆盖叉号。标题默认使用 `红队(3球)` / `蓝队(3球)` 形式，改名后同步替换名称但保留红蓝色。左侧阵容编辑器仍只服务配置者，不进入视频画面；
- `free_for_all`：三个至八个互相敌对的阵营，默认每方一个活跃主球；
- `boss`：BOSS 战，完整沿用 `free_for_all` 的阵营数、出场顺序、寻敌、出生、碰撞、胜负与 HUD；仅小球参数使用独立持久化文件。阵营可以改名、加球和排序，不自动指定或强化任何球；
- `team_brawl`：两个阵营，每方多个主球同时上场；

除单挑外，所有模式都会在主球头顶绘制持续上下浮动的向下阵营三角；同队统一颜色，主球使用大标识，具备独立作战意义的分身、浮游炮、植物、坦克、棋子护卫和列车车厢使用同色小标识。子弹、范围场、轨迹、拾取物和纯特效不显示标识。附属单位被捕获停用时隐藏标识，永久转移所有权后随 `owner_side` 立即切换到新阵营颜色。

非单挑玩法的阵营显示名与稳定阵营 ID、固定队色相互独立。默认名称依次为红队、蓝队、黄队、紫队等；用户改名后，标题、HUD、擂台落败提示、获胜提示、对局日志和录制重演都读取同一份 `BattleSetup` 名称。改名不得改变阵营编号、出生位置、头顶三角颜色、目标选择或伤害归属。

整数 `side` 永远表示稳定阵营 ID；每个上场主球另有单调递增且本局唯一的 `fighter_uid`。实体和状态继续用 `owner_side` / `source_side` 判断敌我，同时用 `owner_fighter_uid` / `source_fighter_uid` 记录真正创建者。同队主球会发生物理分离和冲量，但不结算能力碰撞伤害或命中回调。敌对主球按 `fighter_uid` 稳定顺序两两碰撞，每一对拥有独立接触冷却。

能力每次更新接收距离最近的存活敌方主球；等距离时选择 `fighter_uid` 较小者。标准投射物沿连续轨迹命中最先相交的任意敌方主球或可受击附属物。球模块只看自己的主球、当前目标和阵营，不读取模式或阵容队列。

战斗没有全局阶段。`BattleSimulation`、`BallBattleContext`、`BallRenderContext` 和公共 HUD 均不提供阶段字段或三段式升级。某个球如果拥有觉醒、成长、形态或技能解锁，其等级、触发条件和升级特效全部属于该球唯一的 `BallAbility`，并在面对所有对手时保持一致。

每个 `BattleSimulation` 接收全局设置中的竞技场宽高，作为该局实际碰撞场地。墙面反弹、投射物边界、射线终点、出生位置和球内 `arena_size()` 查询使用同一个实例值；两队模式使用左右阵营锚点，多方模式按阵营数环形生成锚点，同一阵营多主球在锚点切线方向等距排布，初速度大小取各自球参数。`BattleView` 的世界缩放只由固定视觉宽度和竞技场宽度决定；改变竞技场高度时保持白框视觉宽度与球体大小不变，并按纵横比增减外层画布高度。视图横向始终保留 120% 世界范围、球体绝不拉伸，顶部阵营血条面板与竞技场白框之间至少保留 20 px 空隙。场地白框是碰撞边界，窗口外框只表示画面裁切范围。需要固定展示大量召唤物状态时，实体可通过通用 HUD 钩子把信息放在所属阵营顶部血条下方的余量中，而不是跟随场内球体移动。

### 2. 核心不知道具体球

模拟器、公共视图和核心契约中禁止出现具体球 ID、球种分支和球种私有字段。核心只调用多态钩子，不通过 `if ball_id == ...` 或 `match ball_id` 分派行为。

### 3. 球之间禁止源码依赖

`scripts/balls/<id>/` 只能引用自身目录或 `scripts/balls/core/`。黑洞不会读取分身球的 `clone_count`；它只操作实现了 `BallEntity.is_absorbable()` 的敌方空间实体。分身、投射物、持续区域、锚点等附属物自动进入统一捕获轨道，纯粒子、光束等无阵营视觉效果不参与战斗交互。

### 4. 私有状态归能力所有

技能计时、分身数量、黑洞激活时间和锤头角度不进入公共 `FighterState`。球的变化应留在自己的能力/实体/状态对象内，避免公共状态袋随球数增长。

### 5. 交互依赖能力，不依赖类型

跨球交互使用稳定能力：

- 可吞噬对象实现 `is_absorbable()`、`attraction_position()`、`absorption_radius()`、`absorption_visual_color()` 和 `absorb()`；吞噬动画与收束粒子沿用对象自身颜色；
- 所有可吞噬对象默认支持 `can_be_captured()`、`disable_for_capture()` 和 `is_captured()`；捕获后保留原阵营与原色，但禁用自主移动、生命周期、碰撞、伤害及原能力查询，由捕获者接管运动直到吞噬；
- 黑洞捕获不改写所有权；所有权转移属于独立的心灵控制能力，不复用本契约；
- 可转移阵营的附属实体实现 `can_transfer_ownership()` 与 `transfer_ownership()`；投射物明确拒绝阵营转移，控制成功后不会因距离变化自动复原；跟随或环绕主人的实体通过 `on_ownership_transferred()` 把自身锚点切换到新主人，并继续由实体自己保持原运动规则；其他实体通过 `set_ownership_visual_color()` 响应控制方染色；
- 拥有独立生命的附属实体通过 `can_receive_attack()` 和 `receive_attack()` 主动声明可受击；攻击方只按自身的线段、圆形或碰撞几何查询且不读取实体类型；通常只结算偶然命中，明确拥有反附属物能力的球也可以通过该通用能力选择目标；
- 有耐久的地形通过 `is_terrain()` 声明，不能仅凭可受击或质量为零推断是否属于地形。吸血鬼在吸附开始、持续维持和吸血结算时排除地形；静止的作战单位仍可作为原有吸血目标。此标识不自动修改碰撞、破坏、捕获或所有权能力；
- 需要真实阻挡敌方大球的附属实体通过 `participates_in_fighter_collision()`、质量和接触冷却钩子主动加入通用大球碰撞；核心统一完成分离、冲量、双方能力伤害和 `after_entity_contact()` 回调，不识别植物、分身或攻击球类型；
- 需要在非单挑场景中被观众识别阵营的独立附属单位实现 `team_marker_world_height()`，必要时再覆盖 `team_marker_world_position()`；公共视图只读取通用归属和视觉锚点，具体球不绘制也不管理阵营三角；
- 标准非穿透投射物按连续运动轨迹选择最先相交的本体或可受击实体，命中后扣血并消除；光束、范围场和其他穿透攻击可命中路径上的多个实体，但不会因命中分身而中断；
- 跨帧状态实现 `blocks_damage()`、`preserves_external_velocity()`、`on_wall_hit()` 等钩子；所有无敌能力复用 `InvulnerabilityStatusEffect`，并统一在最上层显示一个金色盾牌；
- 非完全免伤的护甲、易伤等状态通过 `modify_incoming_damage()` 修正入伤；默认原样返回，主球与附属单位共用此钩子。完全免伤优先处理，修正后才扣血并计入实际伤害账本，状态不自行扣血、回血或改写统计；
- 需要“停止世界”的能力通过 `request_world_stop()` 申请有限时长的通用停顿；核心冻结对局计时、主球、状态、实体生命周期、投射物和所有普通能力，只允许发起者通过 `on_world_stop_step()` 推进自身变身表现，核心不识别发起球种；
- 需要响应本体墙面反弹的被动能力覆盖 `BallAbility.after_wall_hit()`；核心只传递墙面碰撞点并记录成功触发，不识别球种，也不保存球种私有墙面状态；
- 持续燃烧复用 `BurnStatusEffect`；调用球必须注入自己的每跳伤害、间隔、持续时间、来源键与颜色，公共状态不得写死任何具体球的燃烧数值；
- 寒冰减速统一复用 `IceSlowStatusEffect`；所有寒冰来源共享唯一状态，重复命中只刷新剩余时间并保留最强倍率，速度上限始终基于首次未减速速度计算，不能按命中次数复乘；
- 通用核心只管理对象生命周期和调用顺序。

独立作战附属物通过 `combat_category()` 声明稳定分类 ID 和公开名称；成长实体在自身模块中按当前形态返回分类，公共账本与结算界面不维护球种或植物形态列表。主球以 `fighter_uid` 区分；实体额外保留创建者身份和攻击来源快照。普通子弹、持续状态继承发射或施加时的单位来源；在能力脚本中代替某个附属物发射子弹、结算双向碰撞时，必须通过通用 `source_unit` 参数传入实际行为者。直接扣除附属物自身损耗时，使用 `record_entity_health_loss()` 记录已实际扣除的数额，不再次扣血。账本只观察已生效的结果，不参与数值、目标选择、碰撞或胜负裁决。

主球与附属实体的接触在调用门控前提供当前撞击者的 `combat_contact_source`。需要“离开后才能再次触发”的静态障碍可按其中的主球 UID 独立记录接触，不能只按阵营合并同队多个撞击者。延后结算的损耗保留该次接触的来源快照。

新增一种可吞噬物时无需修改黑洞；修改黑洞时无需修改分身球、浮游炮、火焰球或植物球。

### 6. 逻辑、表现、音效分离

能力通过 `BallBattleContext` 产生伤害、实体、视觉原语和通用战斗事件。实体通过 `BallRenderContext` 绘制场内形态；需要固定界面信息时可覆盖 `draw_hud()`，该钩子只接收所属一侧的大血条区域，不能取得具体模拟器。公共视图只转发事件给战斗音频系统，不认识某一种技能。球模块可以为事件声明自己的 `AudioStream` 短采样；未声明采样的事件继续使用程序合成音，播放设备和混音生命周期仍由通用音频系统统一管理。拥有明确命名招式的动漫或角色球在主动发招时，使用通用表现实体显示短时招式名，并由自身模块同步发送对应语音事件；公共视图不保存角色名单，也不判断具体招式。主球生命首次降到零时，核心只触发一次通用 `fighter_death` 事件并生成不参与战斗、固定绘制在活跃主球下方的死亡特效实体；胜负已确定但结果卡保持隐藏，直至全局揭晓延迟结束。

球体之间的普通碰撞只处理位置分离、冲量、反弹和通用碰撞特效，默认不造成伤害。只有当“本体撞击”明确属于该球的能力时，球自己的 `BallAbility.contact_damage()` 才返回正数；锤头、投射物、分身或持续区域的命中由对应能力或实体独立结算。

### 7. 组合没有特殊规则

项目不提供特殊场景注册、球档案或按对手切换能力的入口。任意阵营、阵容和球种组合都只读取各球模块唯一的配置、能力和视觉；新增某个视频题材不能创建组合专用规则。

### 8. 确定性优先

战斗以 60 Hz 固定步长推进。出生方向、玩法和视觉各使用一条由种子派生的独立随机流：所有实际上场的主球依稳定阵营、阵容和 `fighter_uid` 顺序，在 360° 内生成方向，速度大小取各自长期保存的球参数；相同 `BattleSetup`、球参数与种子必须得到相同换人、目标、碰撞、方向和快照，增减粒子和残影不能改变球的轨迹或胜负。任何模式都有可配置硬时限；时限到达时按“存活主球生命 + 未上场候补满生命 / 整队最大生命”裁决，平比由阵营 ID 决定。

### 9. 信息密度服从观感

竞技场内的通用浮动文字只用于伤害和治疗数值。球自己的能力升级、无敌、分裂、黑洞牵引与吞噬使用色环、粒子、残影和符号表达，避免短视频画面被说明文字遮挡。唯一例外是动漫或角色球的命名主动招式：发招瞬间可在施法球上方短时显示招式名，并且必须与对应语音同时出现；常驻被动、持续伤害和普通碰撞不得反复刷名称。

### 10. Godot 自动化优先

开发、调试和验证优先使用 Godot MCP 与 CLI：结构化场景或编辑器操作优先走 Godot MCP，构建、测试、无头运行和批量生成优先走 CLI。只有 MCP 与 CLI 无法完成目标，或确实需要最终人工视觉验收时，才使用 Godot GUI。可重复执行的项目流程不得依赖 GUI 点击。

### 11. 参数归球并长期保存

每个球在自己的 `module.gd` 中声明参数 Schema。所有会改变战斗结果、数量或运动规则的数值，包括本体生命、速度、半径、冷却、伤害、治疗、范围、持续时间、概率、数量上限，以及有生命附属物的生命值，都必须成为该球的可配置参数；纯绘制坐标、颜色通道、音频采样率和数值误差常量不进入玩法配置。

本体生命值默认均为 100，只有明确用作耐久陪练目标的测试球按当前默认配置使用 1000；有独立生命的附属物通常默认 10。`BallRegistry` 只按球 ID 把覆盖值交给所属模块，不解释具体参数。球参数持久化层保存完整的“球 ID → 参数字典”，不提供会随每局重置的全局球属性，也不允许一个球的配置覆盖另一个球。

### 12. 全局规则独立持久化

确实属于一个玩法内所有组合的规则与生产参数进入 `GlobalGameSettings`，不伪装成某个球参数，也不散落在组合分支或主界面控件里。五种玩法共用同一个 Schema，但由 `GlobalSettingsStore` 按玩法 ID 保存五份相互隔离的值；全局设置与球设置仍使用独立 Schema、独立文件和独立弹窗。前者拥有当前玩法的默认对局时限、竞技场宽高、录制帧率、胜负揭晓延迟、擂台落败提示、伤害数字表现，后者只拥有具体球的本体、能力和附属物属性。

玩法全局值由 `Main` 在创建战斗时显式注入 `BattleSimulation`；模拟器和视图不直接读取用户文件，也不需要感知配置属于哪个玩法。命令行 `--time-limit` 的优先级高于当前玩法的持久化默认时限，但只影响当前进程且不会回写文件。测试直接注入默认或指定值，不读取开发者机器上的个人配置。

## 工程规范

| 关注点 | 规范 |
| --- | --- |
| 源码所有权 | 一个球的配置、能力、外观、附属实体和状态全部放在 `scripts/balls/<id>/`；不要把球种逻辑放入公共核心。 |
| ID 与目录 | `<id>` 使用小写蛇形命名，目录名、模块 `id` 和 CLI 参数保持一致；公开中文名只由 `module.gd` 的 `name` 定义。 |
| 依赖方向 | 球目录只能加载自身文件和 `scripts/balls/core/`；禁止加载另一个球目录或 UI。 |
| 状态归属 | 技能计时器、能力等级、形态、计数器和缓存属于对应 `BallAbility`、`BallEntity` 或 `BallStatusEffect`；不得扩张公共 `FighterState`。 |
| 阵营与主球 | `side` / `owner_side` / `source_side` 只表示阵营；需要区分同队创建者时使用核心自动注入的 `fighter_uid` / `owner_fighter_uid` / `source_fighter_uid`，不得用数组位置或 `1 - side` 推导敌人。 |
| 模式隔离 | 球模块不得读取 `BattleSetup.mode`、候补队列或同时上场数。核心用最近敌方目标、通用实体契约和稳定阵营规则让同一球自然进入所有模式。 |
| 参数 Schema | 基础属性和所有玩法数值由所属球的 `module.gd` 声明 `label/default/min/max/step`；能力和实体通过 `setting()`、`settingf()` 或 `settingi()` 读取，不在实现中重复写死。 |
| 参数持久化 | 参数按球 ID 长期保存。开始、重开或切换对局不得重置；恢复默认只影响明确选择的那个球。公共存储和弹窗不得识别具体球 ID。 |
| 玩法全局设置 | 时限、竞技场尺寸、录制帧率、胜负揭晓延迟、擂台落败提示、伤害数字表现由 `GlobalGameSettings` 统一定义，并按玩法 ID 独立长期保存；不得把具体球属性放入全局 Schema，也不得为具体球组合覆盖这些值。 |
| 成长归属 | 禁止全局阶段。球的觉醒、成长和技能解锁只能由自己的唯一 `BallAbility` 保存与推进，公共 HUD 不显示统一阶段。 |
| 战斗访问 | 能力只使用 `BallBattleContext`；需要新的通用能力时先扩展窄接口并证明至少适用于多个球，不能透传模拟器。 |
| 随机性 | 玩法随机只使用 `battle.random_*()`；纯视觉随机只使用表现随机流。禁止用系统时间或全局随机数改变玩法。 |
| 伤害与治疗 | 球本体统一调用 `battle.damage()`；可受击附属实体通过 `battle.damage_entity()` 结算。攻击通常用 `damageable_entities*()` 按自身几何查找附带命中；公开能力明确支持反附属物时，可按确定性几何规则选取可受击实体且默认主球优先。治疗统一调用 `battle.heal()`；只有能力明确声明时才允许超出本体生命上限。 |
| 本体碰撞 | 默认只反弹且伤害为零；禁止在 `module.gd` 或 `FighterState` 配置基础碰撞伤害。只有把撞击写进公开能力的球才能覆盖 `contact_damage()`。 |
| 附属实体 | 投射物优先使用 `add_projectile()`；自定义武器、区域、召唤物继承 `BallEntity`，并声明其生命周期、可吞噬能力；有独立生命且需要承受攻击时实现通用受击契约，需要阻挡大球时再独立选择加入大球碰撞契约。 |
| 跨帧状态 | 无敌、牵引、护盾和持续增益/减益继承 `BallStatusEffect`，使用稳定 `key` 支持刷新、去重和显式移除；可受击附属实体也可承载持续伤害与行动减速类状态，并按状态提供的倍率减慢自身行动步长；通用无敌使用 `InvulnerabilityStatusEffect`；通用燃烧使用 `BurnStatusEffect`，且玩法数值必须由调用球注入。 |
| 绘制边界 | 球本体由 `BallVisual` 绘制，附属物由自身 `draw()` 绘制：`draw_layer <= 0` 位于球体下方，`draw_layer > 0` 位于球体上方；固定实体信息由可选 `draw_hud()` 绘制，普通状态覆盖层由 `draw_overlay()` 绘制，必须压住球内信息的状态标识由 `draw_topmost_overlay()` 最后绘制；公共视图只提供通用区域，不增加技能专用分支。 |
| 信息密度 | 通用战场浮字只保留伤害和治疗数值；技能说明改用形状、色环、残影、粒子和声音表达。动漫或角色球的命名主动招式可在发招瞬间短时显示招式名，但必须与该招式语音一一对应，常驻被动与持续结算不得刷名。 |
| 能力介绍 | 球模块保存完整 UTF-8 观众文案，只讲能力规则、有效目标、战斗结果、限制与反制；不写冷却、伤害、时长、范围、概率等可调数值，不讲配色、形状、动画、粒子、特效、招式字幕、音效或语音，也不写配置项、实现原理、内部判定或开发术语。卡片详情、悬浮提示、复制按钮和录制滚动区复用同一份格式化结果；旧持久化文案违反规则时自动回退到模块默认简介。全局 UI 和手绘文字统一使用具备完整中文覆盖的系统字体，原始文案、搜索、复制与日志不注入不可见排版字符。模块校验必须拒绝违规内容、替换字符和常见双重编码乱码。 |
| 音效 | 能力发送通用 `combat_event`；球模块可声明事件对应的短采样，未声明时由程序音频系统合成。持续型采样显式声明 `loop: true`，同名正强度事件开始循环、零强度事件停止，暂停、重开与对局裁决统一清理。球模块不直接操作音频设备，不得与其他球重复注册同一事件采样。 |
| 死亡演出 | 主球生命首次归零时统一隐藏败方本体，播放位于活跃主球下方的碎裂爆散实体和低频死亡声；局部淘汰不能用上层爆炸覆盖候补或幸存球，结果卡、完成信号与外层结果文字只能在整局胜负确定并经过全局揭晓延迟后出现。死亡表现不得写进具体球模块。 |
| 开发期迁移 | 当前开发阶段修改 ID、字段或契约时只保留一个事实源，删除废弃字段、兼容适配和回退加载器。 |
| 验证 | 每次新增球必须通过模块校验、架构守卫、默认对局回归、全异种组合测试和视觉烟测；测试验证机制与配置边界，不锁定平衡胜率。 |

## 变更隔离标准

修改球 A 时，正常改动面只能是：

```text
scripts/balls/A/**
tests/** 中 A 的行为测试
README 的球说明（公开规则变化时）
```

以下情况视为架构回归：

- 为新增或修改球而编辑 `BattleSimulation`、`BattleView` 或另一个球目录；
- 在核心中加入具体球 ID；
- 把球种计时器或计数器加入 `FighterState`；
- 公共视图增加 `_draw_<某技能>`；
- 球 A 直接加载球 B 的脚本；
- 为某个组合创建场景、球档案、专用模拟器或专用视图。

“不影响其他球”指源码、私有状态和模块加载相互隔离。球 A 的伤害或技能规则发生变化后，与它对战的胜率随之变化属于预期的游戏交互。

## 新增任意类型能力球

项目本地提供 [`add-ability-ball` Skill](.agents/skills/add-ability-ball/SKILL.md)，用于从需求设计、模块实现到完整验收的一次性新增流程。

最小球模块包含三个文件：

```text
scripts/balls/<id>/
├── module.gd   # 参数 Schema、说明、音效类型、能力/视觉入口
├── ability.gd  # 私有状态、逐帧逻辑和技能钩子
└── visual.gd   # 球本体和专属外观
```

复杂球可以继续在同一目录增加：

- `*_entity.gd`：投射物、分身、区域、武器或其他非本体对象；
- `*_effect.gd`：无敌、牵引、持续增益/减益；

### 按行为选择扩展点

| 球的行为 | 首选实现 |
| --- | --- |
| 瞬时伤害、治疗、冲刺、改速 | 在 `ability.gd` 的 `activate()` 或逐帧钩子中调用 `BallBattleContext`。 |
| 标准直线弹丸 | 调用 `battle.add_projectile()`，不要新建重复的通用投射物类。 |
| 武器、分身、区域、轨道、召唤物 | 新建继承 `BallEntity` 的 `*_entity.gd`，由实体拥有位置、生命周期、行为和绘制。 |
| 有独立生命的附属实体 | 实现 `can_receive_attack()` 与 `receive_attack()`；普通攻击通过圆形/线段查询结算偶然命中，明确拥有反附属物能力的球可仅依赖该通用契约主动选取目标。 |
| 无敌、护盾、牵引、持续增益/减益 | 新建继承 `BallStatusEffect` 的 `*_effect.gd`，通过 `battle.apply_status()` 应用。 |
| 球本体外观、蓄力提示、常驻装饰 | 在 `visual.gd` 中实现；如果表现依赖能力私有状态，通过 `BallVisual.ability` 只读访问。 |
| 与其他球的通用交互 | 实现或扩展能力契约，不读取对方类型、ID 或私有字段。 |

### `module.gd` 必填配置

| 字段 | 约束 |
| --- | --- |
| `id` | 与目录一致、全局唯一、小写蛇形命名。 |
| `name` | 面向视频与 UI 的公开名称。 |
| `color` / `accent` | 球本体主色与技能强调色，保证深色背景可辨识。 |
| `max_hp` / `speed` / `radius` | 必须为正数；本体 `max_hp` 默认使用 100。它们会自动进入该球的持久化参数。 |
| `cooldown` | 固定的基础技能冷却；球如需动态冷却，只能在自己的能力中覆盖。碰撞伤害不属于模块配置。 |
| `tuning` | 该球的全部额外玩法参数 Schema；每项声明 `label/default/min/max/step`，整数再声明 `kind: "int"`。有生命附属物的生命值默认使用 10。 |
| `ability` | 选球弹窗、复制按钮和录制滚动区直接展示的完整观众说明。用完整语句讲清能力规则、有效目标、结果、限制与反制；禁止写冷却、伤害、时长、范围、概率等可调数值，禁止讲配色、形状、动画、特效、字幕、音效或语音，也禁止写配置入口、持久化、内部判定、实现原理或关键词链。 |
| `sound_kind` | 使用程序音频系统已有的通用事件类型。 |
| `sort_order` | 控制选择器和球库展示顺序，不能与 ID 承担同一职责。 |

### 能力生命周期

| 钩子 | 用途 |
| --- | --- |
| `on_battle_started()` | 创建开局常驻实体或初始化需要战场上下文的状态。 |
| `before_motion()` | 在球体移动前更新计时、速度或方向相关状态。 |
| `speed_multiplier()` | 返回临时速度倍率，不直接修改公共基础速度。 |
| `on_step()` | 执行持续技能、周期检测和实体协作。 |
| `on_world_stop_step()` | 仅在自己发起的世界停顿期间推进变身等表现状态；不得借此移动、攻击或推进普通技能。 |
| `activate()` | 执行自动冷却触发的主动技能。 |
| `after_entities_step()` | 在附属实体更新后做命中或区域汇总。 |
| `contact_damage()` | 默认返回 `0`；仅当本体撞击明确属于该球能力时，计算本次碰撞伤害。 |
| `after_contact()` / `after_damage_dealt()` | 处理接触后或造成伤害后的球内连锁效果。 |
| `after_wall_hit()` | 响应本体真实墙面反弹；返回 `true` 表示本次撞墙触发了一次球内被动能力。 |

### 实现步骤

注册表会自动发现 `module.gd`，无需维护球名单。

1. 明确球的核心循环、触发条件、伤害来源、反制方式和可视识别符号，避免只堆数值。
2. 明确普通球体碰撞是否无伤害；只有“本体撞击”属于公开能力时才覆盖 `contact_damage()`，不能在模块里填写基础碰撞伤害。
3. 创建 `scripts/balls/<id>/module.gd`、`ability.gd` 和 `visual.gd`，在模块中绑定能力与视觉脚本。
4. 按行为类型选择 `BallEntity`、`BallStatusEffect` 或通用投射物，不在能力脚本中维护并行实体数组。
5. 为新增规则补行为测试；至少覆盖技能触发、伤害/治疗、实体清理、确定性和关键反制交互。
6. 运行 Godot MCP 脚本校验，再运行 README“验证”章节的完整 CLI 测试。
7. 用该球分别对战一个近战球、一个远程球和一个附属物球，检查配置是否生效、机制是否触发、画面密度、音效节奏和硬时限裁决。
8. 更新球库表格和公开能力说明；只有公开架构或使用方式变化时才修改其他 README 章节。

### 完成标准

- 新目录内聚，除核心契约外无跨球源码依赖。
- 注册表自动发现模块，UI 和 CLI 可选择新球。
- 同一种子重复运行得到相同快照，视觉随机不改变胜负。
- 战斗核心、上下文和公共 HUD 均无全局阶段；可成长球的等级只存在于该球唯一能力中。
- 与没有碰撞能力的球相撞时只反弹、不扣血；如果本球拥有碰撞能力，则只有本球一侧造成相应伤害。
- 新实体能正常过期、移除或被吞噬，不残留隐形伤害源。
- 战场文字、粒子和音效清晰但不过载；顶部血条和计时器仍可读。
- 默认对局、全部异种组合、视觉烟测和架构守卫全部通过；不要求特定球获胜或达到预设胜率。
- README 球库表格包含新球 ID、公开名称和简短能力说明。

## 关键架构决策与取舍

| 决策 | 原因 | 代价 |
| --- | --- | --- |
| 模块化单体，而不是每球独立场景或完整 ECS | 保持代码直观、批量模拟快，同时获得清晰模块边界 | 多态契约文件比早期脚本更多 |
| 能力型实体，而不是核心数组加类型分支 | 新实体和新交互可以独立扩展 | 实体必须遵守生命周期接口 |
| 组合无特例，而不是场景编排 | 同一个球面对任何对手都只使用自己的唯一配置和脚本 | 不能为单条视频偷偷注入组合专用规则 |
| 能力私有成长，而不是全局三阶段 | 一个球升级不会改变另一个球的伤害、速度、冷却或渲染上下文 | 每个成长型能力需要自行提供状态、触发规则和视觉反馈 |
| 自动发现 + 架构静态守卫 | 新增球零注册改动，违规依赖在测试期失败 | 模块入口和目录命名必须规范 |
| 球内 Schema + 按球持久化 | 调参跨对局生效，新增参数不修改存储、弹窗或其他球 | 每个玩法数值都必须维护范围和 UI 标签 |
| 全局 Schema + 玩法档案 + 显式注入 | 每种玩法内部共享一个时限和场地事实源，五种玩法的持久化值相互隔离，模拟器仍不依赖用户文件 | 新增全局规则必须证明它与具体球和具体组合无关，并进入全部玩法档案的同一 Schema |
| 统一队伍与阵容运行时，而不是每模式一套引擎 | 单挑、接力、多方和多主球共享物理、能力、实体、状态、录制与日志事实源 | 模拟器和 HUD 必须面向集合，并维护主球 UID 与阵营归属 |

统一模式运行时的完整决策、上限、失败处理与备选方案见 [ADR-0005](docs/adr/0005-unified-team-and-roster-battle-runtime.md)。

## 故障边界

- 模块缺少能力/视觉或 ID 重复：启动前失败并报告具体模块；
- 实体过期或被吞噬：统一由核心生命周期回收；
- 非法零种子：回退到默认种子 `20260815`；
- 球参数文件缺失、损坏或版本不支持：忽略文件并使用各球自己的 Schema 默认值；
- 球参数越界或类型无效：所属球按自己的 Schema 归一化，不影响其他球；
- 玩法全局设置文件缺失、损坏、版本不支持或当前玩法尚无档案：该玩法使用 120 秒和 640×640 等默认值，不影响其他玩法；
- 玩法全局设置越界或类型无效：只在当前玩法档内按全局 Schema 截断或恢复该项默认值；
- 同一结算帧所有阵营均失去最后一个主球且没有候补可接替：判为平局，不使用阵营顺序制造胜者；
- 未分胜负：达到当前对局硬时限后按剩余生命比例裁决；
- 阵营少于两个、ID 重复、阵容为空、球 ID 未注册、阵营/阵容/同时上场数越界：`BattleSetup` 在创建模拟器前拒绝；
- 当前目标死亡：下一钩子前重新按距离和 `fighter_uid` 选择存活敌人；没有敌人时停止激活依赖目标的能力；
- 跨球引用、核心球 ID、第二套引擎或公共技能绘制器：架构测试失败。

## 一键生成竖屏视频

macOS 入口 / Linux 生产主机：

```bash
./tools/render_video.sh 20260815
```

界面中的录制菜单和脚本共用同一条确定性生产链路。Mac 入口通过 `tools/production-host.local.json` 指定的 Linux 生产主机录制，将当前源码与参数快照交给该主机，使用原生 MP4 MovieWriter 将 1080×1920 RGB 帧直接送入 FFmpeg 编码，保留独立的 720×1280 逻辑母版、完整战斗和滚动战报。视频采用 H.264，音轨采用 AAC；不再生成 AVI，也不再对整段视频进行第二次压缩。封面单独提取为 `.cover.jpg`，视频首帧保持原始战斗画面。MP4 验证通过后自动下载到本机 `builds/`。

首次使用录制需要准备 Godot、FFmpeg 和 `tools/native_mp4` 原生写入扩展。Linux 主机执行 `bash tools/native_mp4/build.sh` 构建扩展；macOS 可复制 `tools/production-host.example.json` 为 `tools/production-host.local.json`，填入自己的 Linux 主机、运行时目录和 SSH 密钥路径。本机配置不会提交到仓库。

录制完成后，左侧会显示可选中复制的视频路径和“打开所在目录”按钮，点击按钮即可打开文件管理器并定位到视频文件。

所有导出视频左上角全程显示半透明作者水印「开源游戏作者：萝卜菌_Channel」，与对战标题分行排列。

单挑视频使用 `ability-ball-<左球>-vs-<右球>-seed-<种子>.mp4` 命名；默认“吸血鬼 VS WDC”沿用精简文件名 `ability-ball-seed-<种子>.mp4`。其他模式使用 `ability-ball-<模式>-<阵容摘要>-seed-<种子>.mp4`，阵容摘要最多保留 96 个安全字符，避免长阵容超过文件名限制。项目中的完整目录为：

```text
<项目目录>/builds/
```

生成任意组合：

```bash
./tools/render_video.sh 20260816 splitter black_hole
./tools/render_video.sh 20260817 sonic flame
./tools/render_video.sh 20260818 garen replicator
```

第四个参数可以临时覆盖视频对局时限且不修改全局设置，例如生成 90 秒上限的黑洞球对局：

```bash
./tools/render_video.sh 20260819 black_hole replicator 90
```

第五个参数指定录制帧率，例如以 60 FPS 生成：

```bash
./tools/render_video.sh 20260819 black_hole replicator 90 60
```

第六个参数指定模式，第七个参数编码各队阵容：队伍之间用 `|`，同队球种按出场顺序用英文逗号分隔。可选的第八个参数按同样队伍顺序用 `|` 编码自定义阵营名；留空或缺少某一项时恢复该位置的默认颜色队名。非单挑录制会把同一阵容和名称传入校验器与 Godot 重演进程，不会降级成左右首球的一对一：

```bash
./tools/render_video.sh 20260820 vampire wdc 120 60 relay 'vampire,wind_swordsman,plant|wdc,black_hole,sniper'
./tools/render_video.sh 20260821 black_hole plant 120 60 free_for_all 'black_hole|plant|sniper|vampire'
./tools/render_video.sh 20260822 wind_swordsman yuri 120 60 team_brawl 'wind_swordsman,splitter,sonic|yuri,replicator,heavy_industry'
./tools/render_video.sh 20260823 vampire wdc 120 60 relay 'vampire,wind_swordsman|wdc,black_hole' '先锋队|守擂队'
```

## 对局日志

实际运行的每一局都会在开始和结束时写日志，包括界面内对局以及视频录制进程的确定性重演。日志位于：

```text
builds/logs/<UTC日期>/<battle-id>.jsonl
```

每局一个 JSONL 文件、两条核心事件：`battle_started` 和 `battle_finished`。正常打完的结束状态为 `completed`；重开、换球、修改参数或关闭进程时，未完成的一局记录为 `interrupted` 并保存具体原因。

日志 Schema 2 包含：UTC 时间与墙钟耗时、进程与 Godot/OS/渲染环境、视频帧率和目标文件、完整 `BattleSetup`、种子、竞技场、时限与固定步长、所有持久化球参数、参战模块 Schema、每个主球的 `fighter_uid` / 阵营 / 阵容序号 / 初始最终位置速度与血量、能力私有状态、状态效果、实体的阵营和创建者归属、换人/淘汰/胜负事件、视觉队列、最终快照和全部统计。日志不会保存环境变量、用户名或认证信息。

如果 Godot 或 FFmpeg 不在 `PATH` 中：

```bash
GODOT_BIN=/Applications/Godot.app/Contents/MacOS/Godot \
FFMPEG_BIN=/opt/homebrew/bin/ffmpeg \
./tools/render_video.sh 20260815
```

- 科比球按单球私有节奏轮换闪电旋风劈与肘击，两招分别播放科比本人“曼巴 out”与“man”原声并同步显示招式名；旋风扫击和前向肘击均通过通用几何命中主球及可受击附属单位，同一次旋风不会对同一目标重复扣血；
- 擂台局部换人且不重置对手、落败提示期间战斗时间与幸存球均冻结、红蓝队事件携带准确落败球和下一位、多方稳定目标与淘汰、双方多主球物理、逐主球对冷却、候补生命裁决和多主球确定性；
- 所有非单挑模式的全部活跃主球、候补视觉和多阵营 HUD 进入真实绘制路径；擂台观众 HUD 的时间、当前球血条和双方出阵模型队列互不重叠，红队由左向中、蓝队由右向中紧凑排列，落败文字按配置字号上浮渐隐；
- 当前 `N×(N−1)/2` 种异种组合均可产生胜者或合法平局并正常结束；有伤害来源的组合产生真实伤害，明确惰性的测试球不会伪造技能或碰撞伤害；
- 所有球、实体、状态效果和动态参数弹窗的真实绘制路径可以加载；
- 按球覆盖、跨组合复用、越界归一化以及保存/重载后配置不串球；
- 全局时限、竞技场宽高、录制帧率以及擂台落败提示时间和字号可持久化；玩法参数跨组合生效并进入真实碰撞与渲染边界，录制帧率只进入视频生产链路。
- 每局日志具有配对的开始/结束事件，并保存可解析的完整模式、阵容、主球 UID、换人事件、状态与统计。

## 主要目录

- `scripts/simulation/`：统一战斗设置与唯一的固定步长战斗模拟器
- `scripts/balls/core/`：稳定球、实体、状态和渲染契约
- `scripts/balls/<id>/`：每种球的全部私有实现
- `scripts/settings/`：全局参数与球参数的 Schema、归一化和本机持久化
- `scripts/logging/`：不参与玩法的结构化对局开始/结束日志
- `scripts/ui/`：唯一战场视图、HUD 和通用视觉原语
- `scripts/audio/`：实时合成的程序音效
- `tests/`：规则回归、架构守卫、全组合和视觉烟测
- `tools/`：竖屏视频生成脚本
