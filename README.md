# Ability Ball Lab

Ability Ball Lab 是一个用 Godot 4 编写的原创程序化“能力球”战斗与短视频生产项目。两个带有独立规则的球在封闭竞技场中依靠初速度、墙面反弹、球体碰撞和显式技能自动战斗；画面、粒子和音效全部由代码实时生成，不依赖外部美术或音频素材。

界面默认选中“吸血鬼 VS 六王球”，但该组合没有任何专用场景、能力档案或数值覆盖。所有球可以任意配对，始终使用同一套通用规则和各自唯一的持久化配置，默认时限为 120 秒。

## 运行

需要 Godot 4.7 或兼容的 Godot 4.x 版本：

```bash
godot --path .
```

操作：

- `空格`：暂停/继续
- `R`：使用相同种子重开
- `N`：使用随机种子重开
- `1`、`2`、`4`：切换演算速度
- 在界面底部输入任意非零整数种子
- 使用左右下拉框选择球，再点击“开始对战”
- 点击录制菜单选择 24、30、60 或 120 FPS，并在后台按当前球、种子和持久化配置完整重演生成 MP4；当前窗口可以继续观看，成片不包含下方选项与操作区
- 点击“全局设置”修改所有组合共用的默认对局时限和实际竞技场宽高
- 点击“球参数”选择任意球，修改该球本体、技能和附属实体参数，再点击“保存并应用”

球参数按球 ID 独立保存在 `user://ability_ball_settings.json`。例如把分身球生命值改为 145、分身上限改为 7 后，它参加任何后续对局都继续使用这组值；其他球保留各自的配置。重开、随机种子、切换对手和重新启动项目都不会恢复默认值。“恢复此球默认”只重置弹窗当前选中的球，并在“保存并应用”后持久化。

全局设置保存在 `user://ability_ball_global_settings.json`，包含默认对局时限、竞技场宽高和录制帧率。竞技场宽高指场地白框内小球真正能够移动、碰撞和战斗的世界区域，不是 macOS 或 Godot 的外层系统窗口。录制帧率可在 24～120 FPS 间设置，默认 60 FPS，只改变成片画面采样，不改变 60 Hz 战斗物理。保存后会立即应用并供所有后续组合使用；默认时限为 120 秒，默认场地为 640×640。

命令行也可以覆盖单局时限：

```bash
godot --path . -- --time-limit=90
```

## 架构总览

项目采用“模块化单体 + 能力契约”。只有一个 `BattleSimulation` 和一个 `BattleView`；所有球及其附属实体都以自动发现的插件模块接入，不存在按组合匹配的特殊场景层。

```text
Main
 ├─ GlobalSettingsStore ─> user://ability_ball_global_settings.json
 ├─ BallSettingsStore ──> user://ability_ball_settings.json
 ├─ BattleLogger ────────> builds/logs/<日期>/<battle-id>.jsonl
 ├─ BallRegistry ───────> balls/<id>/module.gd + 该球参数覆盖
 └─ BattleView ─────────> BattleSimulation
                            │
                            ├─ BallAbility
                            ├─ BallEntity
                            └─ BallStatusEffect

依赖方向：具体球 → 稳定契约 → 通用核心
禁止方向：通用核心 → 具体球；球 A → 球 B
```

### 运行时调用链

1. `Main` 启动时分别读取全局设置和球参数。全局设置决定所有新对局的时限、竞技场尺寸与录制帧率；球参数按球 ID 交给 `BallRegistry`。创建或重开对局不会清空两类配置。
2. `BallRegistry` 扫描 `scripts/balls/*/module.gd`，校验每个球自己的参数 Schema，应用该球的覆盖值后按 `sort_order` 生成唯一球库；UI、CLI、测试和视频工具都读取这份球库。
3. `BattleSimulation` 接收已归一化的全局时限与竞技场尺寸，根据两个球模块各自唯一的配置创建 `FighterState` 和 `BallAbility`；两个球分别在 360° 内按种子生成可复现的初始方向，并以 60 Hz 固定步长推进物理与技能。
4. `BallAbility` 只通过 `BallBattleContext` 造成伤害、治疗、生成实体、施加状态、读取确定性随机数和发送通用战斗事件。
5. `BallEntity` 与 `BallStatusEffect` 各自管理附属物和跨帧状态；核心只调用稳定生命周期，不识别具体球种。
6. `BattleView` 读取模拟快照，并将球体、附属物、可选实体 HUD 和状态覆盖层的绘制委托给 `BallVisual`、`BallEntity` 和 `BallStatusEffect`；表现层不能反向修改玩法状态。

### 核心组件

| 组件 | 单一职责 |
| --- | --- |
| `GlobalGameSettings` | 声明所有组合共享的参数 Schema，并统一归一化时限、竞技场尺寸与录制帧率 |
| `GlobalSettingsStore` | 读写本机全局持久化参数；不保存任何球属性 |
| `BallSettingsStore` | 读写按球 ID 分组的本机持久化参数；不识别具体球种 |
| `BattleLogger` | 为每局写入独立 JSONL 开始/结束事件，收集配置、运行环境、状态与统计，不参与战斗规则 |
| `BallRegistry` | 扫描 `scripts/balls/*/module.gd`，校验 Schema、应用对应球的参数覆盖并注册球模块 |
| `BattleSimulation` | 固定步长、物理、碰撞、生命值、实体/状态生命周期和胜负 |
| `BattleView` | HUD、通用粒子、通用光束，并通过契约调用模块绘制 |
| `BallModule` | 球的公开配置、参数 Schema、当前有效值以及唯一能力与视觉入口 |
| `BallAbility` | 球的私有运行状态与全部技能规则 |
| `BallBattleContext` | 能力访问战场的窄接口；提供伤害、治疗、实体、状态、随机数和事件 |
| `BallEntity` | 投射物、分身、火焰区、锚点、轨道等非球本体对象的统一行为、世界绘制及可选 HUD 接口 |
| `BallStatusEffect` | 无敌、黑洞牵引等跨帧状态及撞墙/受伤钩子 |
| `BallRenderContext` | 实体绘制所需的只读坐标、时间和查询接口，不暴露玩法进度状态 |

## 架构原则

### 1. 一个运行时事实源

所有组合都由 `BattleSimulation` 演算、由 `BattleView` 展示。组合只决定左右两侧使用哪个球，不得选择另一套能力脚本、参数档案、出生规则或物理规则。

战斗没有全局阶段。`BattleSimulation`、`BallBattleContext`、`BallRenderContext` 和公共 HUD 均不提供阶段字段或三段式升级。某个球如果拥有觉醒、成长、形态或技能解锁，其等级、触发条件和升级特效全部属于该球唯一的 `BallAbility`，并在面对所有对手时保持一致。

每个 `BattleSimulation` 接收全局设置中的竞技场宽高，作为该局实际碰撞场地。墙面反弹、投射物边界、射线终点、出生位置和球内 `arena_size()` 查询使用同一个实例值；左右球统一出生在场地宽度的 25% 与 75%、高度的 50%，初速度大小取各自球参数。`BattleView` 显示竞技场至少 120% 的世界范围，外层画布可以是长方形并使用等比缩放，绝不拉伸球体；顶部血条面板与竞技场白框之间至少保留 20 px 空隙。场地白框是碰撞边界，窗口外框只表示画面裁切范围。需要固定展示大量召唤物状态时，实体可通过通用 HUD 钩子把信息放在所属一侧顶部血条下方的余量中，而不是跟随场内球体移动。

### 2. 核心不知道具体球

模拟器、公共视图和核心契约中禁止出现具体球 ID、球种分支和球种私有字段。核心只调用多态钩子，不通过 `if ball_id == ...` 或 `match ball_id` 分派行为。

### 3. 球之间禁止源码依赖

`scripts/balls/<id>/` 只能引用自身目录或 `scripts/balls/core/`。黑洞不会读取分身球的 `clone_count`；它只操作实现了 `BallEntity.is_absorbable()` 的敌方空间实体。分身、投射物、持续区域、锚点等附属物自动进入统一捕获轨道，纯粒子、光束等无阵营视觉效果不参与战斗交互。

### 4. 私有状态归能力所有

技能计时、分身数量、黑洞激活时间和锤头角度不进入公共 `FighterState`。球的变化应留在自己的能力/实体/状态对象内，避免公共状态袋随球数增长。

### 5. 交互依赖能力，不依赖类型

跨球交互使用稳定能力：

- 可吞噬对象实现 `is_absorbable()`、`attraction_position()`、`absorption_radius()`、`absorption_visual_color()` 和 `absorb()`；吞噬动画与收束粒子沿用对象自身颜色；
- 所有可吞噬对象默认支持 `can_be_captured()`、`disable_for_capture()` 和 `is_captured()`；捕获后保留原阵营与原色，但禁用自主移动、生命周期、碰撞、伤害及原能力查询，由捕获者接管运动直到吞噬；
- 黑洞捕获不改写所有权；所有权转移属于独立的心灵控制能力，不复用本契约；
- 拥有独立生命的附属实体通过 `can_receive_attack()` 和 `receive_attack()` 主动声明可受击；攻击方只按自身的线段、圆形或碰撞几何查询，不读取实体类型，也不把它加入主动瞄准候选；
- 标准非穿透投射物按连续运动轨迹选择最先相交的本体或可受击实体，命中后扣血并消除；光束、范围场和其他穿透攻击可命中路径上的多个实体，但不会因命中分身而中断；
- 跨帧状态实现 `blocks_damage()`、`preserves_external_velocity()`、`on_wall_hit()` 等钩子；
- 通用核心只管理对象生命周期和调用顺序。

新增一种可吞噬物时无需修改黑洞；修改黑洞时无需修改分身球、浮游炮、火焰球或六王球。

### 6. 逻辑、表现、音效分离

能力通过 `BallBattleContext` 产生伤害、实体、视觉原语和通用战斗事件。实体通过 `BallRenderContext` 绘制场内形态；需要固定界面信息时可覆盖 `draw_hud()`，该钩子只接收所属一侧的大血条区域，不能取得具体模拟器。公共视图只转发事件给程序音频系统，不认识某一种技能。

球体之间的普通碰撞只处理位置分离、冲量、反弹和通用碰撞特效，默认不造成伤害。只有当“本体撞击”明确属于该球的能力时，球自己的 `BallAbility.contact_damage()` 才返回正数；锤头、投射物、分身或持续区域的命中由对应能力或实体独立结算。

### 7. 组合没有特殊规则

项目不提供特殊场景注册、球档案或按对手切换能力的入口。任意两个球组合时，通用核心只读取双方球模块各自唯一的配置、能力和视觉；新增某个视频题材不能创建组合专用规则。

### 8. 确定性优先

战斗以 60 Hz 固定步长推进。出生方向、玩法和视觉各使用一条由种子派生的独立随机流：两个球的初始方向分别在 360° 内随机，速度大小取各自长期保存的球参数；相同组合与相同种子必须得到相同方向和相同快照，增减粒子和残影不能改变球的轨迹或胜负。任何对局都有可配置硬时限和生命值裁决，不允许批量录制挂死。

### 9. 信息密度服从观感

竞技场内的浮动文字只用于伤害和治疗数值。球自己的能力升级、无敌、分裂、黑洞牵引与吞噬使用色环、粒子、残影和符号表达，避免短视频画面被说明文字遮挡。

### 10. Godot 自动化优先

开发、调试和验证优先使用 Godot MCP 与 CLI：结构化场景或编辑器操作优先走 Godot MCP，构建、测试、无头运行和批量生成优先走 CLI。只有 MCP 与 CLI 无法完成目标，或确实需要最终人工视觉验收时，才使用 Godot GUI。可重复执行的项目流程不得依赖 GUI 点击。

### 11. 参数归球并长期保存

每个球在自己的 `module.gd` 中声明参数 Schema。所有会改变战斗结果、数量或运动规则的数值，包括本体生命、速度、半径、冷却、伤害、治疗、范围、持续时间、概率、数量上限，以及有生命附属物的生命值，都必须成为该球的可配置参数；纯绘制坐标、颜色通道、音频采样率和数值误差常量不进入玩法配置。

本体生命值默认统一为 100；有独立生命的附属物默认生命值为 10。`BallRegistry` 只按球 ID 把覆盖值交给所属模块，不解释具体参数。球参数持久化层保存完整的“球 ID → 参数字典”，不提供会随每局重置的全局球属性，也不允许一个球的配置覆盖另一个球。

### 12. 全局规则独立持久化

确实属于所有组合的规则与生产参数进入 `GlobalGameSettings`，不伪装成某个球参数，也不散落在组合分支或主界面控件里。全局设置与球设置使用独立 Schema、独立文件和独立弹窗：前者拥有默认对局时限、竞技场宽高与录制帧率，后者只拥有具体球的本体、能力和附属物属性。

全局值由 `Main` 在创建战斗时显式注入 `BattleSimulation`；模拟器和视图不直接读取用户文件。命令行 `--time-limit` 的优先级高于持久化默认时限，但只影响当前进程且不会回写文件。测试直接注入默认或指定全局值，不读取开发者机器上的个人配置。

## 工程规范

| 关注点 | 规范 |
| --- | --- |
| 源码所有权 | 一个球的配置、能力、外观、附属实体和状态全部放在 `scripts/balls/<id>/`；不要把球种逻辑放入公共核心。 |
| ID 与目录 | `<id>` 使用小写蛇形命名，目录名、模块 `id` 和 CLI 参数保持一致；公开中文名只由 `module.gd` 的 `name` 定义。 |
| 依赖方向 | 球目录只能加载自身文件和 `scripts/balls/core/`；禁止加载另一个球目录或 UI。 |
| 状态归属 | 技能计时器、能力等级、形态、计数器和缓存属于对应 `BallAbility`、`BallEntity` 或 `BallStatusEffect`；不得扩张公共 `FighterState`。 |
| 参数 Schema | 基础属性和所有玩法数值由所属球的 `module.gd` 声明 `label/default/min/max/step`；能力和实体通过 `setting()`、`settingf()` 或 `settingi()` 读取，不在实现中重复写死。 |
| 参数持久化 | 参数按球 ID 长期保存。开始、重开或切换对局不得重置；恢复默认只影响明确选择的那个球。公共存储和弹窗不得识别具体球 ID。 |
| 全局设置 | 所有组合共享的时限、竞技场尺寸和录制帧率由 `GlobalGameSettings` 定义并长期保存；不得把球属性放入全局 Schema，也不得为具体组合覆盖这些默认值。 |
| 成长归属 | 禁止全局阶段。球的觉醒、成长和技能解锁只能由自己的唯一 `BallAbility` 保存与推进，公共 HUD 不显示统一阶段。 |
| 战斗访问 | 能力只使用 `BallBattleContext`；需要新的通用能力时先扩展窄接口并证明至少适用于多个球，不能透传模拟器。 |
| 随机性 | 玩法随机只使用 `battle.random_*()`；纯视觉随机只使用表现随机流。禁止用系统时间或全局随机数改变玩法。 |
| 伤害与治疗 | 球本体统一调用 `battle.damage()`；可受击附属实体通过 `battle.damage_entity()` 结算。攻击用 `damageable_entities*()` 按自身几何查找附带命中，不能用它改写主动瞄准。治疗统一调用 `battle.heal()`。 |
| 本体碰撞 | 默认只反弹且伤害为零；禁止在 `module.gd` 或 `FighterState` 配置基础碰撞伤害。只有把撞击写进公开能力的球才能覆盖 `contact_damage()`。 |
| 附属实体 | 投射物优先使用 `add_projectile()`；自定义武器、区域、召唤物继承 `BallEntity`，并声明其生命周期、可吞噬能力；有独立生命且需要承受攻击时再实现通用受击契约。 |
| 跨帧状态 | 无敌、牵引、护盾和持续增益/减益继承 `BallStatusEffect`，使用稳定 `key` 支持刷新与去重。 |
| 绘制边界 | 球本体由 `BallVisual` 绘制，附属物由自身 `draw()` 绘制，固定实体信息由可选 `draw_hud()` 绘制，状态覆盖层由 `draw_overlay()` 绘制；公共视图只提供通用区域，不增加技能专用分支。 |
| 信息密度 | 战场浮字只保留伤害和治疗数值；技能说明改用形状、色环、残影、粒子和声音表达。 |
| 音效 | 能力发送通用 `combat_event`，由程序音频系统播放；球模块不直接操作音频设备。 |
| 开发期迁移 | 当前开发阶段修改 ID、字段或契约时只保留一个事实源，删除废弃字段、兼容适配和回退加载器。 |
| 验证 | 每次新增球必须通过模块校验、架构守卫、默认对局回归、全异种组合测试和视觉烟测；测试验证机制与配置边界，不锁定平衡胜率。 |

## 变更隔离标准

修改球 A 时，正常改动面只能是：

```text
scripts/balls/A/**
tests/** 中 A 的行为测试
README 的球说明（公开规则变化时）
```

以下情况视为架构回归：

- 为新增或修改球而编辑 `BattleSimulation`、`BattleView` 或另一个球目录；
- 在核心中加入具体球 ID；
- 把球种计时器或计数器加入 `FighterState`；
- 公共视图增加 `_draw_<某技能>`；
- 球 A 直接加载球 B 的脚本；
- 为某个组合创建场景、球档案、专用模拟器或专用视图。

“不影响其他球”指源码、私有状态和模块加载相互隔离。球 A 的伤害或技能规则发生变化后，与它对战的胜率随之变化属于预期的游戏交互。

## 新增任意类型能力球

项目本地提供 [`add-ability-ball` Skill](../.agents/skills/local/add-ability-ball/SKILL.md)，用于从需求设计、模块实现到完整验收的一次性新增流程。

最小球模块包含三个文件：

```text
scripts/balls/<id>/
├── module.gd   # 参数 Schema、说明、音效类型、能力/视觉入口
├── ability.gd  # 私有状态、逐帧逻辑和技能钩子
└── visual.gd   # 球本体和专属外观
```

复杂球可以继续在同一目录增加：

- `*_entity.gd`：投射物、分身、区域、武器或其他非本体对象；
- `*_effect.gd`：无敌、牵引、持续增益/减益；

### 按行为选择扩展点

| 球的行为 | 首选实现 |
| --- | --- |
| 瞬时伤害、治疗、冲刺、改速 | 在 `ability.gd` 的 `activate()` 或逐帧钩子中调用 `BallBattleContext`。 |
| 标准直线弹丸 | 调用 `battle.add_projectile()`，不要新建重复的通用投射物类。 |
| 武器、分身、区域、轨道、召唤物 | 新建继承 `BallEntity` 的 `*_entity.gd`，由实体拥有位置、生命周期、行为和绘制。 |
| 有独立生命的附属实体 | 实现 `can_receive_attack()` 与 `receive_attack()`；攻击能力通过圆形/线段查询结算偶然命中，不把附属实体加入主动瞄准。 |
| 无敌、护盾、牵引、持续增益/减益 | 新建继承 `BallStatusEffect` 的 `*_effect.gd`，通过 `battle.apply_status()` 应用。 |
| 球本体外观、蓄力提示、常驻装饰 | 在 `visual.gd` 中实现；如果表现依赖能力私有状态，通过 `BallVisual.ability` 只读访问。 |
| 与其他球的通用交互 | 实现或扩展能力契约，不读取对方类型、ID 或私有字段。 |

### `module.gd` 必填配置

| 字段 | 约束 |
| --- | --- |
| `id` | 与目录一致、全局唯一、小写蛇形命名。 |
| `name` | 面向视频与 UI 的公开名称。 |
| `color` / `accent` | 球本体主色与技能强调色，保证深色背景可辨识。 |
| `max_hp` / `speed` / `radius` | 必须为正数；本体 `max_hp` 默认使用 100。它们会自动进入该球的持久化参数。 |
| `cooldown` | 固定的基础技能冷却；球如需动态冷却，只能在自己的能力中覆盖。碰撞伤害不属于模块配置。 |
| `tuning` | 该球的全部额外玩法参数 Schema；每项声明 `label/default/min/max/step`，整数再声明 `kind: "int"`。有生命附属物的生命值默认使用 10。 |
| `ability` | 一行简短能力摘要，不写规则说明长句。 |
| `sound_kind` | 使用程序音频系统已有的通用事件类型。 |
| `sort_order` | 控制选择器和球库展示顺序，不能与 ID 承担同一职责。 |

### 能力生命周期

| 钩子 | 用途 |
| --- | --- |
| `on_battle_started()` | 创建开局常驻实体或初始化需要战场上下文的状态。 |
| `before_motion()` | 在球体移动前更新计时、速度或方向相关状态。 |
| `speed_multiplier()` | 返回临时速度倍率，不直接修改公共基础速度。 |
| `on_step()` | 执行持续技能、周期检测和实体协作。 |
| `activate()` | 执行自动冷却触发的主动技能。 |
| `after_entities_step()` | 在附属实体更新后做命中或区域汇总。 |
| `contact_damage()` | 默认返回 `0`；仅当本体撞击明确属于该球能力时，计算本次碰撞伤害。 |
| `after_contact()` / `after_damage_dealt()` | 处理接触后或造成伤害后的球内连锁效果。 |

### 实现步骤

注册表会自动发现 `module.gd`，无需维护球名单。

1. 明确球的核心循环、触发条件、伤害来源、反制方式和可视识别符号，避免只堆数值。
2. 明确普通球体碰撞是否无伤害；只有“本体撞击”属于公开能力时才覆盖 `contact_damage()`，不能在模块里填写基础碰撞伤害。
3. 创建 `scripts/balls/<id>/module.gd`、`ability.gd` 和 `visual.gd`，在模块中绑定能力与视觉脚本。
4. 按行为类型选择 `BallEntity`、`BallStatusEffect` 或通用投射物，不在能力脚本中维护并行实体数组。
5. 为新增规则补行为测试；至少覆盖技能触发、伤害/治疗、实体清理、确定性和关键反制交互。
6. 运行 Godot MCP 脚本校验，再运行 README“验证”章节的完整 CLI 测试。
7. 用该球分别对战一个近战球、一个远程球和一个附属物球，检查配置是否生效、机制是否触发、画面密度、音效节奏和硬时限裁决。
8. 更新球库表格和公开能力说明；只有公开架构或使用方式变化时才修改其他 README 章节。

### 完成标准

- 新目录内聚，除核心契约外无跨球源码依赖。
- 注册表自动发现模块，UI 和 CLI 可选择新球。
- 同一种子重复运行得到相同快照，视觉随机不改变胜负。
- 战斗核心、上下文和公共 HUD 均无全局阶段；可成长球的等级只存在于该球唯一能力中。
- 与没有碰撞能力的球相撞时只反弹、不扣血；如果本球拥有碰撞能力，则只有本球一侧造成相应伤害。
- 新实体能正常过期、移除或被吞噬，不残留隐形伤害源。
- 战场文字、粒子和音效清晰但不过载；顶部血条和计时器仍可读。
- 默认对局、全部异种组合、视觉烟测和架构守卫全部通过；不要求特定球获胜或达到预设胜率。
- README 球库表格包含新球 ID、公开名称和简短能力说明。

## 关键架构决策与取舍

| 决策 | 原因 | 代价 |
| --- | --- | --- |
| 模块化单体，而不是每球独立场景或完整 ECS | 保持代码直观、批量模拟快，同时获得清晰模块边界 | 多态契约文件比早期脚本更多 |
| 能力型实体，而不是核心数组加类型分支 | 新实体和新交互可以独立扩展 | 实体必须遵守生命周期接口 |
| 组合无特例，而不是场景编排 | 同一个球面对任何对手都只使用自己的唯一配置和脚本 | 不能为单条视频偷偷注入组合专用规则 |
| 能力私有成长，而不是全局三阶段 | 一个球升级不会改变另一个球的伤害、速度、冷却或渲染上下文 | 每个成长型能力需要自行提供状态、触发规则和视觉反馈 |
| 自动发现 + 架构静态守卫 | 新增球零注册改动，违规依赖在测试期失败 | 模块入口和目录命名必须规范 |
| 球内 Schema + 按球持久化 | 调参跨对局生效，新增参数不修改存储、弹窗或其他球 | 每个玩法数值都必须维护范围和 UI 标签 |
| 全局 Schema + 显式注入 | 所有组合共享一个时限和场地事实源，模拟器仍不依赖用户文件 | 新增全局规则必须证明它与具体球和具体组合无关 |

## 故障边界

- 模块缺少能力/视觉或 ID 重复：启动前失败并报告具体模块；
- 实体过期或被吞噬：统一由核心生命周期回收；
- 非法零种子：回退到默认种子 `20260815`；
- 球参数文件缺失、损坏或版本不支持：忽略文件并使用各球自己的 Schema 默认值；
- 球参数越界或类型无效：所属球按自己的 Schema 归一化，不影响其他球；
- 全局设置文件缺失、损坏或版本不支持：使用 120 秒和 640×640 默认值；
- 全局设置越界或类型无效：按全局 Schema 截断或恢复该项默认值；
- 未分胜负：达到当前对局硬时限后按剩余生命比例裁决；
- 跨球引用、核心球 ID、第二套引擎或公共技能绘制器：架构测试失败。

## 一键生成竖屏视频

macOS / Linux：

```bash
./tools/render_video.sh 20260815
```

界面中的录制菜单和脚本共用同一条确定性生产链路：Godot Movie Maker 使用 1080×1920 原生渲染目标，按所选 24～120 FPS 重演对局；录制呈现模式不创建下方选项区。FFmpeg 从母版顶部直接裁取原生 1080×1200 内容并编码为 H.264/AAC MP4，不做低分辨率放大。最终视频第 1 帧会自动替换成封面帧：画面取自开局后约 0.5 秒，对决标题居中覆盖在内容区上部；从第 2 帧起恢复正常录制画面。封面不增加视频时长、不移动音频，也不额外生成独立图片。成片写入 `builds/`。

视频文件使用 `ability-ball-<左球>-vs-<右球>-seed-<种子>.mp4` 命名；默认“吸血鬼 VS 六王球”沿用精简文件名 `ability-ball-seed-<种子>.mp4`。项目中的完整目录为：

```text
<项目目录>/builds/
```

生成任意组合：

```bash
./tools/render_video.sh 20260816 splitter black_hole
./tools/render_video.sh 20260817 heaven sonic
./tools/render_video.sh 20260818 hammer replicator
```

第四个参数可以临时覆盖视频对局时限且不修改全局设置，例如生成 90 秒上限的黑洞球对局：

```bash
./tools/render_video.sh 20260819 black_hole replicator 90
```

第五个参数指定录制帧率，例如以 60 FPS 生成：

```bash
./tools/render_video.sh 20260819 black_hole replicator 90 60
```

## 对局日志

实际运行的每一局都会在开始和结束时写日志，包括界面内对局以及视频录制进程的确定性重演。日志位于：

```text
builds/logs/<UTC日期>/<battle-id>.jsonl
```

每局一个 JSONL 文件、两条核心事件：`battle_started` 和 `battle_finished`。正常打完的结束状态为 `completed`；重开、换球、修改参数或关闭进程时，未完成的一局记录为 `interrupted` 并保存具体原因。

日志包含：UTC 时间与墙钟耗时、进程与 Godot/OS/渲染环境、运行模式、视频帧率和目标文件、种子、竞技场、时限与固定步长、所有持久化球参数、参战模块 Schema、双方初始/最终位置速度与血量、能力私有状态、状态效果、实体与视觉队列、胜者、结束原因、最终快照和全部统计。日志不会保存环境变量、用户名或认证信息。

如果 Godot 或 FFmpeg 不在 `PATH` 中：

```bash
GODOT_BIN=/Applications/Godot.app/Contents/MacOS/Godot \
FFMPEG_BIN=/opt/homebrew/bin/ffmpeg \
./tools/render_video.sh 20260815
```

## 验证

```bash
godot --headless --path . --editor --quit
godot --headless --path . --script res://tests/test_architecture.gd
godot --headless --path . --script res://tests/test_battle.gd
godot --headless --path . --script res://tests/test_roster_battle.gd
godot --headless --path . --script res://tests/test_roster_view.gd
godot --headless --path . --script res://tests/test_battle_logger.gd
godot --headless --path . --quit-after 120
```

测试分别证明：

- 核心零球种知识、球间零引用、单引擎和通用绘制边界；
- 默认对局、组合无特例、双方唯一配置、代表性机制和确定性；
- 当前 `N×(N−1)/2` 种异种组合均可结束、产生真实伤害并触发专属能力；
- 所有球、实体、状态效果和动态参数弹窗的真实绘制路径可以加载；
- 按球覆盖、跨组合复用、越界归一化以及保存/重载后配置不串球；
- 全局时限、竞技场宽高和录制帧率可持久化；玩法参数跨组合生效并进入真实碰撞与渲染边界，录制帧率只进入视频生产链路。
- 每局日志具有配对的开始/结束事件，并保存可解析的完整配置、状态与统计。

## 主要目录

- `scripts/simulation/`：唯一的固定步长战斗模拟器
- `scripts/balls/core/`：稳定球、实体、状态和渲染契约
- `scripts/balls/<id>/`：每种球的全部私有实现
- `scripts/settings/`：全局参数与球参数的 Schema、归一化和本机持久化
- `scripts/logging/`：不参与玩法的结构化对局开始/结束日志
- `scripts/ui/`：唯一战场视图、HUD 和通用视觉原语
- `scripts/audio/`：实时合成的程序音效
- `tests/`：规则回归、架构守卫、全组合和视觉烟测
- `tools/`：竖屏视频生成脚本
