# ADR-0005：统一阵营、候选队列与多主球战斗运行时

## 状态

Accepted

## 日期

2026-08-24

## 背景

现有战斗运行时固定保存 `left`、`right` 两个 `FighterState`，并让整数 `side` 同时承担阵营 ID、主球 ID、附属物所有者和 HUD 位置四种含义。这个模型只能表达一对一对战，无法正确支持以下规则：

- 两个阵营各自拥有候选队列，当前主球死亡后只替换己方主球，敌方位置、生命、速度、技能计时、状态和附属物完全不重置；
- 三个及以上互相敌对的阵营同时混战；
- 两个阵营各有多个同时存活、独立施法和独立承伤的主球。

如果分别实现三套模拟器或模式分支，同一球会在不同模式下经过不同的碰撞、伤害、目标选择和生命周期路径，组合数量增长后难以保证确定性与模块隔离。底层改造还必须保持固定 60 Hz 演算、同种子可复现、球模块不知道具体模式，并让录制、日志和可视化共享同一事实源。

## 决策

### 一个统一战斗设置

新增规范化的 `BattleSetup`。它包含模式 ID 和若干阵营，每个阵营声明：

- 稳定阵营 ID 与显示名称；
- 有序球种候选列表；
- 初始同时上场数量。

三种新增模式只生成不同设置，不创建专用模拟器：

- `relay`：两个阵营，初始各上场一个，剩余候选按顺序接替；
- `free_for_all`：至少三个阵营，默认每方上场一个；
- `team_brawl`：两个阵营，每方可同时上场多个主球；
- 原一对一模式是两个阵营、各一个候选、各上场一个的普通设置。

模拟器只接收规范化设置，不读取 UI 控件、用户文件或命令行。

### 阵营 ID 与主球运行时 ID 分离

整数 `side` 的稳定语义改为“阵营 ID”。`BallEntity.owner_side`、状态来源和现有球模块的敌我判断继续使用阵营 ID，因此同阵营对象天然友好，任意不同阵营天然敌对。

每个实际上场的主球获得单调递增的 `fighter_uid`。模拟器以有序主球集合推进能力、物理和绘制，并通过 `fighter_uid` 映射其模块、能力、碰撞冷却和所有附属物。球模块仍只得到自己的 `fighter`、当前目标和阵营 ID，不接触模式类型或候选队列。

附属实体增加可选的 `owner_fighter_uid`。`BallBattleContext` 在能力或实体执行期间维护当前来源作用域，新增实体和投射物会自动绑定到真正的创建主球。所有权转移同时更新阵营与主球归属。这样某个主球死亡时只清理仍归属于它的对象，不会删除同阵营其他主球的召唤物，也不会误删已经倒戈的对象。

### 统一目标选择

每个主球在自己的更新开始时选择最近的存活敌方主球；距离相同时按 `fighter_uid` 决定，保证确定性。这个目标传入原有能力钩子。能力或实体通过 `opponent_for_side()` 延迟查询目标时，战斗上下文优先使用当前执行来源的位置选择最近敌方；没有来源作用域时使用阵营的确定性主主球。

主球目标优先规则仍保留：一个攻击几何同时覆盖主球和附属物时，具体能力继续优先结算主球。不存在存活敌方时不激活需要目标的能力。

### 物理、伤害与附属物

主球两两进行物理分离和冲量：同阵营主球也会物理碰撞以避免重叠，但只有不同阵营之间才会结算能力碰撞伤害和命中回调。每对主球拥有独立接触冷却，不再共享一个全局计时器。

参与主球碰撞的附属实体会与所有敌方存活主球检测，而不是通过 `1 - owner_side` 推导唯一目标。实体对实体、投射物、控制、捕获和吞噬继续依赖通用能力契约。

### 死亡、接替与胜负

主球生命首次归零时立即播放现有通用死亡演出。死亡演出属于已经退场的主球并固定绘制在所有活跃主球下方，不能覆盖立即入场的候补或相邻幸存球。运行时随后处理所属阵营：

- 若该阵营还有候选且当前存活数低于初始上场数量，先把接替请求加入稳定队列；通用死亡演出期间暂停玩法演算，演出结束后才在死亡位置创建下一个主球；新主球满生命、使用新能力实例和新技能计时，初始方向来自同一对局的确定性出生随机流；
- 敌方和其他友方的全部运行时状态保持原对象、原数值，不重建模拟器；
- 死亡主球的状态和仍归属于它的附属物被清理；
- 没有存活主球且候选耗尽时，该阵营淘汰。

仅剩一个未淘汰阵营时结束战斗。硬时限到达时按阵营“当前存活生命 + 未上场候选满生命”除以该阵营整队最大生命计算剩余比例；比例相同时按阵营 ID 判定，保证可复现。

### 表现、日志与兼容边界

`BattleView` 遍历全部存活主球及其视觉实例，不按球种或模式分支绘制。顶部 HUD 按阵营分区并显示存活数、候选数和队伍总生命；球内仍显示各自主球生命。结果卡显示获胜阵营及其剩余主球。

日志 Schema 升级并记录完整 `BattleSetup`、所有阵营、候选进度、全部主球及其 `fighter_uid`、模块、能力、状态和实体归属。录制标题由阵营阵容生成，不再假设只有两个球 ID。

旧的一对一构造入口可以在迁移期间转换成普通 `BattleSetup`，但模拟器内部只保留阵营和主球集合这一份事实；完成 UI、测试和工具迁移后不保留第二套双人演算路径。

## 非功能要求

- 确定性：同设置、同球参数、同种子必须产生相同出生顺序、目标选择、碰撞顺序、接替顺序和结果快照；
- 性能：主球碰撞采用确定顺序的 O(n²) 配对，首期限制为最多 8 个阵营、每阵营最多 16 个同时主球和 32 个候选，适合短视频规模且无需 ECS；
- 可维护性：球模块只依赖现有核心契约，不读取模式 ID、队列或具体对手类型；
- 可观测性：开始与结束日志必须保存设置、队列进度、替换事件、淘汰事件和逐阵营统计；
- 安全性：设置只接受注册表中已有球 ID，并限制阵营、候选和同时上场数量；不加载外部脚本或路径；
- 故障收束：非法设置在开局前拒绝；没有合法敌方目标时安全跳过技能；任何模式仍受硬时限裁决。

## 后果

### 正面

- 擂台、多方混战、双方多球和原一对一共享一套物理、技能、实体、状态与胜负规则；
- 替换己方主球无需重建战斗，其他所有对象可以原样保留；
- `side` 保持阵营语义，绝大多数现有球模块无需理解多主球或模式；
- `fighter_uid` 消除同阵营多主球的伤害来源、附属物归属和碰撞冷却歧义；
- 后续可以自然组合“多方 + 多主球 + 候选队列”，无需增加第四套模式。

### 负面

- 模拟器、渲染上下文、日志和大量双人测试需要一次性迁移；
- 少数直接使用 `1 - side` 或假设每阵营唯一主球的球内实体需要改用通用目标查询或明确的创建者引用；
- 主球数量增加后碰撞与目标查询成本按平方增长，因此必须保留规模上限和性能回归。

### 中性

- 同阵营主球会互相产生物理轨迹影响，但不会互伤；这是大混战的通用空间规则，不提供组合级开关；
- 接替球使用死亡位置而不是固定出生点，能保持战局连续性，也可能立即处于危险区域；不做无敌或平衡补偿。

## 考虑过的方案

### 为三种模式各建一个模拟器

实现局部直接，但能力、碰撞和状态会形成多份事实源，任何新球都要验证多套引擎，因此不采用。

### 把每个主球都视为独立阵营

可以复用当前 `side`，但同队主球及其附属物会互相伤害，无法表达团队胜负和队列，因此不采用。

### 继续让 `side` 同时表示阵营和主球

少改接口，但同阵营多主球的实体归属、伤害回调、状态来源和目标选择无法无歧义实现，因此不采用。

### 引入完整 ECS

能够统一实体数据，但当前规模有限且球能力高度异构，迁移成本与调试复杂度超过收益，因此不采用。

## 失败处理

- 阵营少于两个、阵营 ID 重复、候选为空、球 ID 未注册或上场数量越界：设置规范化失败，战斗不启动；
- 当前目标在本帧死亡：下一能力钩子前重新选择目标，不保留失效引用；
- 同帧多个阵营全部死亡：先按稳定阵营/主球顺序完成可用接替；仍有候补的一方继续战斗，最终所有阵营均无主球且无候补时判为平局，不按阵营顺序指定胜者；
- 接替位置不适合新球半径：只把新主球限制回竞技场，不移动任何其他对象；
- 时限比例相同：阵营 ID 较小者获胜并在日志中标记确定性平局裁决。
