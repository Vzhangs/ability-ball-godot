# ADR-0004：全局对局设置与动态竞技场

## 状态

Accepted

## 日期

2026-08-16

## 背景

项目已经按球 ID 长期保存每种球的生命、能力和附属物参数，但默认对局时限仍由主界面单局输入和代码默认值共同决定，竞技场则固定为 640×640。时限存在多个事实源，场地宽高无法从运行界面调整。

默认对局时限和可对战区域都适用于所有球与所有组合，不属于某一种球，也不应由具体组合负责。竞技场尺寸如果只改变白框绘制而不改变物理边界，会造成画面与玩法不一致。

## 决策

新增独立的 `GlobalGameSettings` Schema，首批包含：

- `battle_time_seconds`：所有新对局的默认硬时限，默认 120 秒，范围 15～600 秒；
- `arena_width`：实际竞技场宽度，默认 640，范围 320～1920；
- `arena_height`：实际竞技场高度，默认 640，范围 320～1920。

全局设置由 `GlobalSettingsStore` 以版本化 JSON 保存到 `user://ability_ball_global_settings.json`。`GlobalSettingsDialog` 根据 Schema 动态生成输入项。保存后主入口更新当前运行时全局值并重开当前对局；重开、切换球、切换种子和应用重启继续使用已保存值。

`Main` 是持久化配置与战斗构造之间的组合根。它分别加载全局设置和按球设置，并在创建 `BattleView` 时显式传入时限与 `Vector2` 竞技场尺寸。`BattleSimulation` 和 `BattleView` 不直接读取用户文件。

`BattleSimulation` 以实例字段保存竞技场尺寸。墙面碰撞、球内 `arena_size()`、投射物边界、射线终点和所有通过战斗上下文进行的场地查询统一使用该值。左右球统一出生在场地宽度的 25% 与 75%、高度的 50%，并把球体限制在合法边界内；球本身的速度不随场地缩放。

`BattleView` 从当前模拟器取得场地尺寸，按原有 120% 可视范围规则进行等比缩放和居中。宽高不等时保留额外留白，不使用非等比拉伸，因此球仍保持圆形。外层 Godot/系统窗口尺寸不随竞技场变化。

具体组合不能覆盖全局时限或竞技场。命令行 `--time-limit` 可以临时覆盖持久化默认时限，但只影响当前进程且不写回全局文件。

## 后果

### 正面

- 所有组合共享一个明确、长期保存的默认时限和竞技场事实源。
- 修改竞技场宽高会真实改变碰撞、移动和技能查询边界，而非仅改变画面。
- 全局规则与球属性保持独立，修改全局设置不要求编辑任何球目录。
- 模拟器仍可通过构造参数独立测试，不依赖本机用户配置。
- 矩形竞技场使用等比渲染，球体和碰撞几何不会被视觉拉伸。

### 负面

- 场地变大但球速不变时，球体接触频率可能降低；这是用户选择的全局规则结果，不做组合平衡补偿。
- 极端长宽比会产生较多画面留白，并可能降低顶部附属物 HUD 的可用空间。
- 新增一种真正的全局规则需要同时维护 Schema、持久化、弹窗和构造注入测试。

### 中性

- 全局设置与按球设置使用两个文件和两个弹窗，生命周期清晰但入口按钮增加一个。
- 默认 640×640、120 秒的无配置行为保持不变。

## 考虑过的方案

### 继续使用单局时限输入框

操作直接，但重启后丢失，且与持久化配置体系不一致，因此不采用。

### 把时限和竞技场放入每个球配置

同一场对局包含两个球，会产生冲突值，也会污染球模块所有权，因此不采用。

### 把全局值放入组合分支

特殊组合可以定制节奏，但同一个全局设置会随对手变化，并重新引入组合级平衡耦合，因此不采用。

### 让模拟器直接读取用户文件

调用代码较少，但纯模拟测试和视频工具会隐式依赖开发者机器状态，破坏依赖方向，因此不采用。

### 调整外层系统窗口而保持 640×640 物理场地

只能改变显示面积，无法满足调整小球实际可对战区域的需求，因此不采用。

## 安全与故障处理

全局文件只包含三个受范围约束的数值，不包含路径、脚本、账号或凭据。缺失、损坏或版本不支持的文件会整体回退到 Schema 默认值；非法类型回退该项默认值；越界值会截断并按步长归一化。保存失败时当前进程继续使用已应用值，界面明确提示无法跨启动保存。

竞技场构造参数在模拟器内还有最小尺寸防线，避免非 UI 调用创建无法容纳球体的负场地。出生点在能力初始化前完成缩放与边界限制。测试不会读取默认用户文件，而是显式注入全局值。
