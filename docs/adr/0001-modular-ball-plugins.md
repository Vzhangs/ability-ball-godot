# ADR-0001：采用自动注册的球模块

## 状态

Accepted

## 背景

球库已经包含 10 个球，但静态数据、能力、外观、音效和命令行白名单分散在多个集中式文件。增加一个球需要修改战斗核心和渲染核心，容易遗漏注册点，也会让两个核心文件持续膨胀。

项目需要支持持续增加球种、任意组合对战、固定种子重放和无界面组合测试。团队规模和部署形态不需要分布式系统；模块边界和低操作成本比独立部署更重要。

## 决策

项目采用模块化单体。每个球在 `scripts/balls/<id>/` 下形成独立模块包：

- `module.gd`：模块清单、静态数值、显示信息和能力/视觉工厂；
- `ability.gd`：战斗行为策略；
- `visual.gd`：绘制策略。

`BallRegistry` 只扫描项目内固定的 `res://scripts/balls/` 目录，校验唯一 ID、必需字段和脚本类型，并按模块声明的顺序生成球库。战斗模拟器依赖 `BallAbility` 契约，视图依赖 `BallVisual` 契约。能力只通过 `BallBattleContext` 的窄接口访问随机数、伤害、治疗、特效和战场查询，不接触模拟器内部集合。UI、CLI 和测试统一读取注册表，不再维护独立白名单。

旧的集中式 `BallCatalog`、能力 `match fighter.id`、视觉 `match fighter.id` 和脚本白名单在迁移完成后删除，不保留兼容适配层。

## 后果

### 正面

- 新增球只需新增一个目录，不修改模拟器、视图、主界面和出片脚本。
- 单个球的规则、外观和配置具有清晰所有权，可以独立测试和替换。
- 核心循环只依赖稳定契约，球数量增长不会扩大核心分支。
- 注册、UI、CLI 和测试共享一个事实来源，避免名单漂移。

### 负面

- 每个球需要三个小文件，文件数量增加。
- Godot 没有语言级接口，契约由基类、注册表校验和测试共同保证。
- 能力需要通过受限的战斗上下文调用公共效果，不能直接修改视图。

### 中性

- 原“吸血鬼 VS 六王球”Boss 场景仍作为独立战斗模式存在；它不参与通用球模块的能力分发。
- 所有模块仍随同一个 Godot 项目发布，不引入动态下载或外部代码执行。

## 考虑过的方案

### 继续使用集中式分发

文件少、实现快，但每个新球都会修改核心，无法满足长期扩展要求。

### 每个球一个完整场景

视觉编辑方便，但物理、状态和能力生命周期容易被场景树细节绑住，确定性纯模拟测试成本更高。

### ECS

适合大量同构实体，但当前只有少量高差异球种，会引入超过需求的抽象和调试成本。

## 失败处理

- 重复 ID、缺失入口或错误脚本类型：注册表拒绝加载并使验证失败。
- CLI 收到未知 ID：在录制前返回非零退出码，不启动战斗。
- 单球能力异常：组合测试明确报告球 ID 和对战组合。
