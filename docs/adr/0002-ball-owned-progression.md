# ADR-0002：成长状态归能力所有

## 状态

Accepted

## 日期

2026-08-16

## 背景

战斗核心曾提供统一的三阶段状态，并由场景根据时间或生命值推进。所有球的伤害、速度、冷却和实体表现都可以读取这一状态，导致一个场景级概念同时改变无关球种，也让公共模拟器、战斗上下文、渲染上下文和 HUD 承担了具体玩法所有权。

项目要求每个球的代码和特性变化不影响其他球。成长、觉醒、形态和技能解锁如果确实属于某个球，就必须与该球一起封装，而不能成为所有组合默认共享的战斗规则。

## 决策

战斗运行时不提供全局阶段。`BattleSimulation`、`BattleScenario`、`FighterState`、`BallBattleContext`、`BallRenderContext`、公共 HUD 和快照均不得保存或传播阶段状态。

需要成长机制的球在自己的 `BallAbility` 中保存等级、触发条件和转换规则。该球的 `BallVisual` 与同目录实体可以只读访问这份能力状态，用于本球的形态、符号和特效。场景只负责选择球档案和通用对局参数，不推进能力等级。

六王球展示档案使用私有“王冠等级”保留逐步解锁效果；其他球不读取该等级，也不会随其变化获得全局增益。

## 理由

- 维持 ADR-0001 确立的球模块所有权和依赖方向。
- 修改一个成长型球时，核心、场景、对手和公共视图无需变化。
- 普通球不再被场景时间轴统一增加伤害、速度或冷却频率。
- 能力状态与对应视觉在同一模块内，行为和表现可以一起测试。

## 考虑过的方案

### 保留全局阶段，只限制部分球读取

实现改动较小，但核心仍保存具体玩法状态，新增代码很容易再次复用它并形成隐式耦合，因此不采用。

### 由场景维护每个球的独立等级

场景可以集中编排展示节奏，但会知道球的能力细节，并使同一球在不同场景中的行为来源不一致，因此不采用。

### 由能力维护私有成长

需要每个成长型球自行实现触发和视觉反馈，但所有权明确、扩展隔离，符合项目长期模块化目标，因此采用。

## 后果

- 通用能力使用固定模块数值；动态成长必须在具体能力中显式实现。
- 公共 HUD 不再绘制三枚阶段菱形，成长提示由球自己的视觉承担。
- 架构测试扫描公共玩法、场景和视图代码，阻止全局阶段字段重新进入。
- 对局平衡会因移除统一后期增益而变化，需要依靠全组合数据继续调整具体能力数值。

## 更新规则

只有当战斗产品定义明确需要所有球共享同一种全局局势状态，并且该状态不能建模为场景参数、实体、状态效果或球私有能力时，才重新评估本决策。任何替代方案仍需保持核心不识别具体球种。
